## 加密不生效：OPT 里 RDP 值写错（已修）

用户反馈"加密了还是能读到芯片校验和"。

对照算法源码说明 `D:\mym\NXN\6.Programmer\DAPlink\烧录算法转换工具\烧录算法转换工具\MM32G001-OPT_ext_说明.txt`：

```
0x00  RDP  读保护: 0x807F=加密, 0x5AA5=不加密
```

而 `tools/chip_config.json` 里 RPO 的"读保护开启"值写的是 **0**，
经 `_generate_opt_bin` 的"低字节=值 + 高字节=反码"打包后变成 **0xFF00**，
芯片不认这个 RDP 值（合法只有 0xA5/0x7F），OPT 判为无效 → 回退默认不保护 → 仍可读。

### 三处 bug
1. `chip_config.json`：RPO 加密选项 `0` → **`127`(0x7F)**，打包出 0x807F（文件 `7F 80`）。
   MM32G0001A 和 MM32SPIN0230 两处都改。
2. `daplink_manager.py`：OPT 文件只生成到最后一个 word（10 字节），
   但算法头 `opt_size=16`，`target_opt_program_ext` 会按 16 字节写，
   后 6 字节取的是 `DATA_BUFFER+2048+10` 处的**上一页固件残留**，会写进 WRP1~3。
   → 新增 `chip.opt_size`，生成定长 16 字节；抽出 `_build_opt_bytes()` 供
   `_generate_opt_bin` 和 `_update_opt_preview` 共用（原来预览也有同样 bug）。
3. 未编程半字原来算成 `0x00FF`（值 0xFF + 反码 0x00），应为 **`0xFFFF`**。
   已加 `low_byte == 0xFF → 0xFFFF`。
4. `run.c` 两处 `f_read(opt)` 前 `memset(DATA_BUFFER+2048, 0xFF, 128)`，
   防止文件短于 opt_size 时把残留字节写进 OPT。

### 验证
生成结果与说明书模板完全一致：
```
加密   7F 80 FF FF FF FF FF FF FF FF FF FF FF FF FF FF
不加密 A5 5A FF FF FF FF FF FF FF FF FF FF FF FF FF FF
```
Python 语法检查通过；固件 0 Error 0 Warning，Code=53164，bin 59872 字节。

### 注意
改了上位机后必须**重新导入固件**，否则 SD 卡上旧的 `<固件名>_opt.bin` 还是错的那份。

## 更新（13:11）：Verify failed (OPT) —— 文件 16B 但 OPT 区后半读不回

## 更新（13:21）：OPT +03 FF>00 —— 高字节必须是低字节的反码

用户屏幕: `OPT +03 FF>00`（offset 3, 期望 FF, 读回 00）。
offset 3 = 0x1FFFF803 = OPT1(USER) 的高字节 = 反码位。

结论: 上一版"未编程半字写 0xFFFF"是**错的**。芯片按"低字节=值, 高字节=~值"
规范化, 写 0xFFFF 读回 0x00FF。正确写法是 0x00FF(值 0xFF + 反码 0x00)。

注意: `MM32G001-OPT_ext_说明.txt` 里模板写的是 `A5 5A FF FF ...`,
与实际读回不符, **以实测为准**, 不要照抄模板。

改动:
1. `daplink_manager.py::_build_opt_bytes` 去掉 `low==0xFF -> 0xFFFF` 特判,
   统一 `value = (~low & 0xFF) << 8 | low`。
   生成: 加密 `7F 80 FF 00 FF 00 FF 00 FF 00`
         不加密 `A5 5A FF 00 FF 00 FF 00 FF 00`（10B）
2. `run.c` OPT 校验只严格比对 **RDP 半字(前 2 字节)**:
   `uint32_t vlen = ulReadNum >= 2 ? 2 : ulReadNum;`
   USER/DATA/WRP 的读回值会被硬件规范化, 逐字节比对必然误报。

构建: 0 Error 0 Warning, Code=53368, bin 60080 字节 (13:21:38)。

## 结论（13:58）：根因是上位机没勾"读保护开启"

用户确认: OPT 面板里的 RPO 一直是默认值 165(不加密), 所以 opt 文件是 `A5 5A`,
芯片当然能读。之前所有"加密不生效"的现象都源于此, 不是固件 bug。
（但排查过程顺带修掉了 3 个真问题: RDP 加密值应为 0x7F、OPT 半字反码规则、
OPT 文件长度应为 10B。）

UI 改进: OPT 预览框右侧新增 `lbl_rdp_state` 状态标签,
`_update_opt_preview` 按 buf[0]|buf[1]<<8 判断:
- 0x5AA5 → 红色「未加密」
- 0x807F → 绿色「已加密」
- 其他   → 橙色「RDP 异常」
配合面板默认展开, 避免再次看漏。

加密后的正常流程(已验证逻辑):
烧录 → mass erase 解除旧保护 → 复位重连 → 编程 → 写 RDP=0x807F
→ 调试口锁 → 断电重启生效。下次烧录重复, 因此"加密"与"能一直烧"并存。

## 更新（16:05）：新增自动烧录（检测到芯片即烧）

硬件依据: PA15 → P-MOS 栅极 → 目标芯片 VCC（`TARGET_PWR_ON` 拉低 PA15），
所以"给电后 SWD 有没有应答"就是可靠的插片检测手段，不需要读 UID
（MM32G0001 的 UID 地址未确认，0x1FFFF7E8 是 STM32/GD32 的）。

### run.c 状态机（文件顶部宏/枚举 + target_connect_halt 之后实现）
```
WAIT(探测) → BURN(mode4 跑原有流程) → RESULT(停 1.5s/3s) → HOLD(等拔片)
HOLD → WAIT 只在连续 2 次探测不到芯片时
```
- `auto_probe()`: `swd_off()` → `TARGET_PWR_ON` → 立刻连续 50 次 `swd_init_debug()`
  (每次 1ms)。**必须在刚上电就开始找**，因为目标 app 可能几 ms 内关掉 SWD；
  这和烧录路径 `target_connect_halt()` 的时序一致，所以"能烧 = 能测到"。
- 防误判: 连续 2 次有/无才算状态翻转；探测间隔 200ms；HOLD 至少停 600ms。
- 关键点: 加密后的芯片若 DP 仍应答 → 一直停在 HOLD 等拔片；若完全不应答 →
  退到 WAIT 后同样探测不到，**不会重复烧同一颗**。
- `mode4` 的 `static done` 提升为文件级 `g_burn_done`；`g_burn_ok` 只在
  `i==bin_size && !opt_failed && opt_state!=2` 时置 1。
- `mode4` 结束（download_return）时若 `g_auto_en`：置 RESULT、记时间戳、回 mode2。
- `show_download_status/error` 把文案存进 `g_last_status[24]`，自动模式的
  FAIL 页第 6 行显示它（否则 mode2 重绘会把错误原因冲掉）。
