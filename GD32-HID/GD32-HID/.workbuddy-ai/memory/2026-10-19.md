## 排查：MM32G0001 只能烧录一次，第二次报 "ER2: Algo init"

结论（待用户验证）：不是 SWD 接线问题，而是每次烧录成功后写入的 OPT 字节
（0x1FFFF800，扩展算法 MM32G001-OPT_ext.bin）在复位后生效，把芯片置成
不可再烧写的状态；另一烧录器的 Erase Chip 会把 OPT 一起清掉，所以"又能烧一次"。

关键代码位置：
- `USER/APP/run.c:476` 调 target_flash_init，失败统一跳到 `run.c:507` 打印 "ER2: Algo init"
- `USER/DAPlink/SWD_flash.c:22-41` ER2 实际合并了 3 个失败点：
  ERROR_RESET（RESET_PROGRAM 失败）/ ERROR_ALGO_DL（写 SRAM 失败）/ ERROR_INIT（算法 init 返回非 0）
- `USER/DAPlink/SWD_host.c:755` swd_wait_until_halted 的 `return 0` 被注释，halt 超时不会报错，
  会继续读 R0 得到垃圾值 → 也表现为 ER2
- 诊断值 `g_last_syscall_r0`（SWD_host.c:733）：0xDEE1/0xDEE2/0xDEE3 或算法返回码，但 ER2 路径未显示
- OPT 流程：`run.c:588-651` 写 OPT，`run.c:717` 复位使其生效；`SWD_opt.c:87-107` 按 opt_size 写入
- 隐患：`run.c:615` 只读 10 字节 opt 文件，`SWD_opt.c:90` 却按 opt_size 写，超出部分是 DATA_BUFFER 残留
- 打包逻辑：`tools/daplink_manager.py:1312-1350`，低字节=值、高字节=反码；OPT0 期望 0x5AA5（字节 A5 5A）
- 配置：`tools/chip_config.json` MM32G0001A，opt_base 0x1FFFF800，RPO 默认 165(0xA5)，WRP0 0xFF

建议改动（未实施）：ER2 拆分 ER2a/b/c + 显示 g_last_syscall_r0；opt_size 与文件长度校验；
改成真正的 connect-under-reset（先拉低 nRST 再上电连接）；烧完保持 halt。

## 更新（16:40）：已实施 + 关键新事实

用户反馈：取消勾选"上传 OPT"后第二次仍然烧不进。但旧代码里
`apply_prepare_download()` 是 `(void)opt_required;`，勾选框只控制"上传"，
不控制"是否写 OPT"——SD 卡上上次上传的 `_opt.bin` 还在，第二次照样会写 OPT。
所以那次测试无效。

用户真实需求：**要开读保护（RPO）加密，同时要能反复烧录**。
这决定了解法方向：RDP1 下 mass erase 是允许的且会清掉 RPO，但 page erase/program
被禁止。正确顺序必须是「整片擦除（顺带解保护）→ 复位 → 编程 → 写 OPT 开 RPO → 复位」。
当前代码 `target_flash_init` 排在 `erase_chip` 之前，保护态下 init 就先失败，
根本走不到擦除 —— 这才是"只能烧一次"的机制。

已改动（USER/APP/run.c、run.h）：
1. 新增 `show_download_error()`：第一行错误码、第二行 `r0=%08lX`（OLED page0/page1）
2. `target_flash_init` 返回值存到 `init_err`，ER2 拆成
   ER2a=ERROR_RESET / ER2b=ERROR_ALGO_DL / ER2c=ERROR_INIT / ER2?=其它
3. `init_diag` 在 `target_flash_uninit` 之前抓取 g_last_syscall_r0（否则被 uninit 覆盖）
4. 删掉 ER2 分支里重复的 target_flash_uninit 调用
5. app_TypeDef 新增 `opt_enable`，`apply_prepare_download` 真正写入该标志；
   OPT 编程与 OPT 校验两处都改为 `is_ext_algo && app_data.opt_enable && ...`
6. mode3 设备端手动选文件时置 opt_enable=1，保持旧行为

待办：确认 ER2 子码后，实现"保护态自动整片擦除解保护 → 复位 → 重新 init"的恢复路径。

## 更新（16:55）：现场回读 r0=0000DEE1

0xDEE1 来自 `SWD_host.c` 的 `swd_flash_syscall_exec()`：`swd_write_debug_state()`
返回 0。该函数有 5 个可能失败点：写 DP_SELECT、写 16 个核心寄存器（DCRSR/DCRDR +
等 S_REGRDY 超时）、写 DHCSR、读 CTRL_STAT、以及**末尾检查 STICKYERR/WDATAERR**。

关键发现（本次新加）：`swd_write_memory()` 用 ACK==OK 判成功，但 AHB-AP 被拒时
第一次传输仍可能 ACK=OK，错误只体现在 CTRL/STAT.STICKYERR 上。也就是说
**"算法 blob 写 SRAM 失败"会被静默吞掉，最后表现成 0xDEE1**，旧代码无法区分。

本次改动：
1. `SWD_host.c`：新增 `swd_diag_capture()`，DEE1 时抓 DP CTRL/STAT 和 DHCSR 到
   `g_diag_ctrl_stat` / `g_diag_hcsr`（SWD_host.h 里 extern）
2. `SWD_flash.c target_flash_init()`：
   - RESET_PROGRAM 失败时用 `swd_read_memory` 抓 DHCSR 存 g_diag_hcsr
   - 写 blob 前先 `DP_ABORT` 清 STICKYERR（复位序列里写 AIRCR 是不查返回值的，
     失败会留下粘滞错误，之后所有 AP 访问都失败）
   - 写 blob 后读 CTRL/STAT，若 STICKYERR|WDATAERR 则返回 ERROR_ALGO_DL（ER2b）
3. `run.c`：init 前清 g_last_syscall_r0 / g_diag_*；错误页显示三行
   `错误码` / `r0 CTRL_STAT` / `H DHCSR`

判读方法：
- cs 含 0x20 → AP 被拒（保护态/总线门控）→ 需要整片擦除解保护
- cs 无 0x20 且 h 的 S_HALT(0x20000)=0 → 核心没停住（看门狗复位/低功耗）
- h 含 S_HALT 且 cs 干净 → 是寄存器传输超时，另有原因

## 更新（17:30）：定位到 RESET_PROGRAM —— 只开 C_DEBUGEN 不停核

用户照片（新固件）：ER2a / step=1 r0=0 / cs=DDDDDDDD / h=DDDDDDDD
判读：init 阶段是 ERROR_RESET（没跑过算法，r0=0）；step=1 是随后 target_flash_uninit
那次 syscall 留下的；cs=h=DDDDDDDD 表示失败后 swd_init_debug() 都救不回来 → 链路已死。

根因推断：`swd_set_target_state_hw(RESET_PROGRAM)` 里第一步只写了
`DBG_HCSR = DBGKEY|C_DEBUGEN`，**没有 C_HALT**，核心仍在跑 APP；随后
`swd_set_target_reset(1); delaymS(20); (0); delaymS(20);` 共 40ms 里 APP 跑完启动、
把 PA13/PA14 复用成 GPIO 或进 STOP，SWD 直接断。若目标板没接 nRST，
`swd_set_target_reset()` 只能靠写 AIRCR 软复位，而那时 AP 已经不可写 → 复位也没发生。

修复：
1. 新增 `swd_halt_core()`（SWD_host.c/h）：写 DHCSR=DBGKEY|C_DEBUGEN|C_HALT 并回读 S_HALT
2. `RESET_PROGRAM` 第一步改成写 `DBGKEY|C_DEBUGEN|C_HALT`，连上就先停核
3. run.c 的连接重试循环：`swd_init_debug()` 成功后立刻 `swd_halt_core()`，
   抢在 APP 改 SWD 之前；失败时区分 "DIS: SWD failed" / "DIS: CPU busy"
4. RESET_PROGRAM 加了 step 码 0x20~0x25，并把原来**无限等待 S_HALT** 的循环
   改成 200 次超时（0x25），避免死等
5. run.c 新增 init_step，错误页显示 `step=%02lX r0=%lX`，不再被 uninit 覆盖

step 码表：0=DP_SELECT 1-4=R0-R3 5=R9 6=R13-15 7=xPSR 8=DHCSR 9=读CTRL_STAT
10=STICKYERR；0x20=swd_init_debug 0x21=写C_DEBUGEN|C_HALT 0x22=写VC_CORERESET
0x23=等halt时读失败 0x24=清VC_CORERESET 0x25=200ms未halt

构建：0 Error 0 Warning，Code=52928，bin 59640 字节。
